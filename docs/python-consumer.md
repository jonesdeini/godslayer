# Python consumer — pipeline shape and design notes (discussed 2026-10-29/30/31)

Dense working notes, kept separate from `CLAUDE.md` for the same reason as `ebay-api.md`: only relevant once actually building the Python consumer, not most other work in this repo. Nothing here is settled architecture - see `CLAUDE.md`'s Open section for what's actually decided vs. still open.

## The pipeline, as currently understood

1. Consume `{listing_id}` off `listing_ready`. **Built.**
2. `GET /api/listings/:id` → metadata + image URLs. **Built.**
3. Download the images. **Built.**
4. Photo-sort — classify which photos are useful (BIOS/iLO screen, DIMM label vs. box art) — no value judgment yet, per `CLAUDE.md`'s funnel-stages note. **Collapsed into extraction for the current MVP** - see `secret_sauce/mvp-strategy.md` (gitignored) for why a separate classification pass isn't built.
5. Extract — read the actual specs off the useful photos, compare against the claim. **Built** (a local LLM distills structured claims from the listing text and separately from the OCR text into a shared schema, then plain code does the actual comparison) - see `secret_sauce/mvp-strategy.md` for why an end-to-end "one model call does extraction and comparison together" approach didn't work reliably.
6. Write the determination back to Rails via `POST /api/listings/:id/determinations`. **Built** - see `CLAUDE.md`'s determinations entry for the settled write-back shape (append-only, `active` flag, raw value+unit pairs, `listing_image_id` pointing at whichever image produced the hit).

Verified end-to-end against real services (2026-10-31): a real RabbitMQ message → real `GET /api/listings/:id` call → a real downloaded image → real Tesseract OCR output. Found and fixed a real bug this way - the API was handing out relative, not absolute, blob URLs (see git history / PR for `app/views/api/listings/show.json.jbuilder`).

## Comparison step - general shape (specifics in `secret_sauce/mvp-strategy.md`)

The determination step splits across two tools, each used for what it's actually reliable at: a local LLM (via Ollama) handles fuzzy text extraction/normalization (robust to OCR noise and varied listing phrasing), and plain deterministic code handles unit conversion and threshold comparison (no LLM arithmetic). Local-only, not a hosted API - a real cost constraint for this project, not a style choice. Model/schema/hardware specifics are in the gitignored strategy doc.

**Model switched from `qwen2.5:14b` to `granite4.2:8b` (2026-11-02/03)** - the original pick was never a deliberate "best available" choice, just the first model tested that worked once the compound-task prompt got split (see the gitignored strategy doc). Checked properly this time against real production data instead of defaulting to "the next version in the same family": ran both models against 96 real cases pulled from this project's own database (40 real claim texts, 56 real OCR'd photo texts, including real BIOS screens and real junk like part-number stickers) with production load quiet so timing wasn't confounded. Result - 95/96 agreement, `granite4.2:8b` ~25% faster on average despite being a smaller model (8B vs 14B, 5.3GB vs 9GB download), and on the one disagreement it was *more* correct: `qwen2.5:14b` hallucinated a RAM value from an SSD drive label's OCR text, `granite4.2:8b` correctly returned no evidence. `granite4.2:8b` is also genuinely new (IBM, released ~Sept 2026) and purpose-built for structured JSON/tool-use output, which is literally what every call in this pipeline does.

## Concurrency - reasoning so far, not yet built against

- Downloading images (step 3) is I/O-bound - threads/async, not multiprocessing, regardless of what extraction ends up being.
- OCR itself (step 5, Tesseract) is CPU-bound, not I/O-bound - multiprocessing/batching is the right lever here if throughput ever becomes a real problem, not async. Not built - current pass processes one image at a time, synchronously, inside message handling.
- If extraction ever calls a hosted vision-capable LLM per image (see `secret_sauce/mvp-strategy.md`'s fallback-path note), that's I/O/rate-limit-bound instead - concurrent requests under a limiter, not raw process count.

## Consumer reliability - a real incident, what caused it, and the fix being built (2026-11-02)

**What happened:** on the first real production sweep (v0.2.0, ~1,800 listings), 636 listings (35%) never got a determination. Dug into why rather than assume - two distinct causes, not one:

1. **Already fixed, a one-off data bug, not a design gap.** `./storage_data` on Shadesmar was root-owned from before Active Storage existed in this app, so the `rails` user (uid 1000) couldn't write to it. During that window, Active Storage still committed blob rows to Postgres (real checksum, real byte size) even though the physical file write failed - so some `ListingImage` rows pointed at files that didn't exist on disk. `ml` 404'd trying to fetch them. Found it, deleted the ~126 affected rows, reset their flags, redownloaded for real, republished. Done - this was a data incident, not something `ml` needs to defend against.
2. **Not fixed yet, a real design gap, and the bigger number.** 757 listings failed with `requests.exceptions.ConnectionError` (`web` unreachable) or a DNS lookup failure, **all within one ~4.4 second window** (14:42:35-14:42:39), exactly when `docker compose up -d` recreated `web` for the v0.2.1 release. Verified this precisely from the real `ml` logs, not assumed - it's one burst, not scattered failures over the day. The mechanism: `channel.basic_consume` has no `basic_qos`/prefetch limit set, so RabbitMQ had already handed `ml` a large batch of ready deliveries; `ConnectionRefusedError`/DNS failures return in milliseconds (no slow timeout to wait on), so the single-threaded consumer tore through 757 of them in just a few seconds while `web` happened to be down. Every one of those got caught by `handle_message`'s bare `except Exception`, logged, and **acked anyway** - permanently discarded, no retry, even though the failure was purely transient and `web` was back within seconds.

**Why PR #19 (graceful `SIGTERM` handling) doesn't fix this:** that PR protects only the *one* message actively being processed at the moment a deploy's signal arrives - it lets that single in-flight callback finish instead of getting killed mid-work. It does nothing for a message that gets delivered, fails with a transient error, and gets acked-and-discarded in the normal course of `handle_message`'s existing exception handling. This incident needed that message to be *retried*, which is a different code path entirely (the `except` block itself, not shutdown handling).

**The fix - built.** `consumer.py`'s `handle_message` now retries in a loop (`MAX_ATTEMPTS = 3`, `RETRY_DELAY_SECONDS = 5`):
- `is_permanent_failure` carves out *known-permanent* failures (currently: a `requests.exceptions.HTTPError` with a 4xx status - the request itself was bad, e.g. a genuinely dead image URL, retrying won't change the outcome) as the exception, rather than an allowlist of *known-retryable* types. Reasoning: the attempt cap already bounds the damage of retrying something that was never going to succeed, so defaulting to retry catches failure modes we haven't anticipated yet (new dependency, new API call, a case nobody's seen) without needing someone to notice and add it to a list first.
- A capped retry count, with a short fixed delay between attempts (not exponential, not multi-tier) - **in-process** (ack the original only once it either succeeds or is finally given up on; retry the same work directly in Python a few times with short gaps in between), not via a RabbitMQ delay queue or plugin. Reasoning, by elimination, not preference: the delay must be held *somewhere*. Holding it in `ml`'s own process (a sleep, `call_later`, a background timer) means it's gone if `ml` itself restarts mid-wait - a real correctness gap, and an ironic one, given the entire point of this feature is surviving restarts. Holding it in RabbitMQ (a TTL+DLX retry queue, or the delayed-message-exchange plugin) is durable and would be the right call *if* a real outage longer than a few seconds ever actually happens - but the only outage observed so far is the ~4 seconds above, and building multi-queue delay infrastructure for a problem that hasn't occurred yet isn't worth it right now. **A short in-process retry (blocking only the one failing message, for a few seconds, not minutes) is small and bounded enough that the "doesn't survive a restart" gap doesn't matter in practice** - a restart mid-retry just means that one message gets redelivered by RabbitMQ anyway (it's still unacked at that point), no different from any other in-flight message during a restart. If a longer real outage ever does show up and this proves insufficient, revisit then - including the plugin, which is on the table precisely because we own the infra, not ruled out forever.
- A message that exhausts its retries, or hits a permanent failure immediately, gets published to a durable `listing_ready.dead` queue (declared in `run`) and the original is acked - not silently discarded. Inspectable/replayable now, and the natural hook for Glitchtip reporting once that exists.

**A real but ultimately inert risk, found checking the above rather than assumed:** `pika`'s `BlockingConnection` doesn't process AMQP heartbeat frames while a message callback is running (it's not pika's event loop, it's our own blocking Python code), so a long enough callback risks RabbitMQ deciding the connection is dead. Checked the real negotiated heartbeat on the live connection (`rabbitmqctl list_connections` → `timeout: 60`) and checked real processing times from today's run: **142 of 1,173 successfully-processed listings already took over 60 seconds, worst case 133 seconds** - `find_photo_ram` loops over every image in a listing sequentially until it finds a hit, each with its own OCR + LLM round trip, so a listing with many photos and no match runs long. Despite repeatedly exceeding the 60s heartbeat timeout, `ml`'s log shows exactly one connection for the entire day - zero disconnects, zero reconnects. So the risk is real and documented (worth knowing if the gap ever gets dramatically larger - a stuck Ollama call, a huge image), but it is **not currently causing any actual problem**, and doesn't need to shape the retry design above.

**Still open, not investigated:** why 142 listings took over 60 seconds, and 648 took over 30 - is that just "many photos, no match, exhaustive loop" as suspected, or something else? Separate question from the retry design above; worth a look once there's time.

## Python tooling, in use

- `python-dotenv` - `.env` loading.
- `pika` - RabbitMQ client, blocking/sync.
- `requests` - the HTTP client for both the Rails read API and downloading images.
- `pytesseract` - thin wrapper around the real Tesseract OCR binary (must be installed on the host separately - not a pure-Python dependency).
