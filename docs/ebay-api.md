# eBay API reference — findings from direct research & testing

Dense reference material, kept separate from `CLAUDE.md` because it's only relevant when actually touching eBay integration code, not most other work in this repo. See `CLAUDE.md` for how this feeds into the app's architecture and decisions.

## Authentication (OAuth2 client_credentials)

- **Dev ID is not used for this grant type.** Verified by reading eBay's official OAuth Node.js client source directly (`eBay/ebay-oauth-nodejs-client`), not docs/blog claims — `request.js`'s `postRequest` builds Basic Auth from only `clientId:clientSecret`, and the POST body is only `grant_type`+`scope`. `devid` is carried in that SDK's config object but never sent anywhere for this flow. Only App ID (client ID) and Cert ID (client secret) matter for what this app does.
- **Sandbox vs. production only changes the host, not the path.** Confirmed from the same SDK's `constants.js`: `api.sandbox.ebay.com` vs. `api.ebay.com`, identical paths (`/identity/v1/oauth2/token`, and by the same eBay-wide convention, `/buy/browse/v1/...`). `Ebay::Base::API_HOSTS` models this as one value, not two full URL pairs.
- **The OAuth scope string does not change between sandbox/production.** `https://api.ebay.com/oauth/api_scope` is a single hardcoded constant in the SDK, not environment-keyed like the host is, and isn't even part of the SDK's per-environment config template (`demo/ebay-config-sample.json` only varies `baseUrl`; scope is a separate runtime argument). It's an opaque permission identifier the auth server matches against, never an endpoint actually requested — both sandbox and production auth servers are configured to recognize the identical string.
- **Real verified test (2026-10-26):** token exchange against the real sandbox endpoint succeeded with real App ID/Cert ID credentials — got back a real ~1940-char token.

## Marketplace header (`X-EBAY-C-MARKETPLACE-ID`)

**Does not filter by item location at all.** It picks which marketplace/site's listing pool you're querying (ebay.com vs. ebay.ca vs. ebay.co.uk, etc.), not where the item or seller is physically located. A Canadian seller listing on ebay.com (`EBAY_US`) shows up in our results same as a US seller — confirmed via the official docs (`ItemSummary` reference: "does not indicate a language preference or consumer location"). Real item-location filtering, if ever wanted, is a separate mechanism (`filter=deliveryCountry:...` or an end-user-context header) — not something `EBAY_US` does for you.

## Browse API search (`/buy/browse/v1/item_summary/search`)

- **Real response shape, confirmed via a live sandbox call (2026-10-26, `q=laptop`):** `href`, `total`, `next`, `limit`, `offset`, `itemSummaries[]`. Matches what was guessed for the abandoned Go version.
- **Sandbox returns synthetic placeholder data**, not real listings — titles like "Sample eBay Listing 0999", auto-incrementing. Good for verifying mechanics (auth, request shape, response parsing all genuinely work), useless for verifying real-world search quality/relevance. That needs production access.
- **Item summaries only include `seller.feedbackScore`, not `seller.username`** — contradicts an assumption carried over from the old Go code. **Confirmed via a real item-detail call (2026-10-26): item detail does have `seller.username`** (e.g. `"testuser_developer514"`), so the summary/detail asymmetry is real but detail covers it.
- **`searchInDescription:true` does not add a description field to the search summary response.** Confirmed via a real paired comparison (same `q`, with/without the filter) — identical response keys either way, no description/snippet text exposed. So self-filtering on description content before paying for a "show" call isn't possible from the summary alone; only title text is visible there. Also inconclusive on whether the filter changes *which* items match at all — sandbox's synthetic data gave identical `total` with and without it (likely because the synthetic titles/descriptions don't meaningfully differ), so that part still needs production data to verify for real.
- **`-term` exclusion syntax on the `q` param is confirmed working, for real, server-side.** Verified 2026-10-26: `q=laptop` → 79 results (most titles mention "RAM"); `q=laptop -ram` → 1 result, and it's the one title that doesn't mention RAM. This is a real, working server-side filter, not a guess — eBay excludes matching listings *before* they ever reach the response, meaning before any downstream "show" call would ever be considered for them. (The earlier "unverified" status here was from docs research alone, before real API access existed — now resolved by an actual call.)
- **OR-grouping and AND are both confirmed working on the `q` param, including nested/quoted combinations.** Verified 2026-10-27 with real sandbox calls: plain space-separated terms are AND (`q=laptop desktop` → 0 results, confirming no single listing has both words); `(term1,term2)` is OR (`q=(laptop,desktop)` → 79 results, including a title with "desktop" but not "laptop" — proves it actually broadened the match, not just ignored the syntax); and the full real-world shape needed — two parenthesized OR-groups, ANDed together, with quoted multi-word members — parses and matches correctly: `q=(laptop,"note book") (dell,"hewlett packard",hp)` → 22 results, all genuinely Dell or HP. This is what lets one `search_keywords` row cover every spacing/capitalization variant of a model name (e.g. `(modelA,"model A") (genX,"gen X",gX,"g X")`) in a single API call instead of needing one row per spelling.
- **Real `itemSummary` field schema, confirmed via a live sandbox call (2026-10-28, `q=laptop`):** `adultOnly`, `availableCoupons`, `buyingOptions`, `categories`, `condition`, `conditionId`, `itemCreationDate`, `itemHref`, `itemId`, `itemLocation`, `itemOriginDate`, `itemWebUrl`, `leafCategoryIds`, `legacyItemId`, `listingMarketplaceId`, `price`, `priorityListing`, `seller`, `shippingOptions`, `title`, `topRatedBuyingExperience`. `price` and `condition` are both present on the cheap search call — enough to detect "did this change since we last stored it" without paying for a per-item detail call at all. The only date fields are `itemCreationDate`/`itemOriginDate` (both creation, not modification) — **no update/revision field exists on `itemSummary`**, confirmed both by this real call and by the official OpenAPI-generated model docs (eBay's Browse API spec, mirrored at e.g. `numerogeek/ebay-browse-api`), which list the full `ItemSummary` schema and it has no `seller_item_revision` or any other modification-tracking field.
- **`sellerItemRevision` exists, but on `Item` (the detail/"show" resource), not `ItemSummary` (search) — corrected after initially, wrongly, assuming it was Feed-API-only** (see Feed section below) purely because that was the only place it had been written down, not because Browse was ever actually checked. Confirmed via the official OpenAPI-generated model docs: `Item`'s schema includes `sellerItemRevision`, described as "an identifier generated/incremented when a seller revises the item" (covers both seller edits and eBay-system changes, e.g. a quantity drop from a sale). **Confirmed present for real in sandbox, on a broad sample, not just one item** (2026-10-28) — the first check (one `laptop` item) was too thin a sample and wrongly suggested sandbox never populates it. Checked across every item from several keyword searches instead: `laptop` (100 items) → 0 had it; `desktop` (5 items) → 3 had it (values `"3"`, `"7"`, `"7"`); `monitor` (7 items) → 2 had it (values `"3"`, `"2"`). So: the key is **absent** (not `null`, not `"0"`) when an item's never been revised, and present as a numeric-looking **string** once it has. Since it only lives on the detail call (not the cheap summary), it can't be used to *avoid* paying for a detail call — its value is as a correctness signal *after* a detail call already happened: gating the `listing_ready` republish on an update, not just on first-seen, which the current design has no mechanism for at all (see `CLAUDE.md`'s publish-on-new-listing design — it only ever fires once, never on a real revision).

## Feed API (`/buy/feed/v1_beta/item`)

- **Needs a different OAuth scope**: `https://api.ebay.com/oauth/api_scope/buy.item.feed`, not the generic Browse API scope.
- **Needs a mandatory `Range` request header** (HTTP byte-range) — a raw call without one gets `400: The mandatory 'Range' request header is missing`. The official Java/Python Feed SDKs abstract this (chunk size 100MB production, 10MB sandbox); a hand-rolled call needs to set it explicitly.
- **Sandbox only supports `feed_scope=NEWLY_LISTED`, not `ALL_ACTIVE`** (bootstrap feeds aren't available there at all). Sandbox's valid `date` window is a trailing ~15-day range ending **2 days** before the current date (confirmed via a real `400` naming the exact valid range, e.g. as of 2026-10-26: `20261010` to `20261024`) — don't guess a date, check the error.
- **Real field schema, confirmed via a live sandbox call (2026-10-26, category `58058` "Computers/Tablets & Networking"):** `ItemId`, `Title`, `ImageUrl`, `Category`, `CategoryId`, `BuyingOptions`, `SellerUsername`, `SellerFeedbackPercentage`, `SellerFeedbackScore`, `GTIN`, `Brand`, `MPN`, `EPID`, `ConditionId`, `Condition`, `PriceValue`, `PriceCurrency`, `PrimaryItemGroupId`, `PrimaryItemGroupType`, `ItemEndDate`, `SellerItemRevision`, `ItemLocationCountry`, `LocalizedAspects`, `SellerTrustLevel`, `Availability`, `ImageAlteringProhibited`, `EstimatedAvailableQuantity`, `AvailabilityThresholdType`, `AvailabilityThreshold`, `ReturnsAccepted`, `ReturnPeriodValue`, `ReturnPeriodUnit`, `RefundMethod`, `ReturnMethod`, `ReturnShippingCostPayer`, `AcceptedPaymentMethods`, `DeliveryOptions`, `ShipToIncludedRegions`, `ShipToExcludedRegions`, `InferredEPID`, `InferredGTIN`, `InferredBrand`, `InferredMPN`, `InferredLocalizedAspects`, `AdditionalImageUrls`, `OriginalPriceValue`, `OriginalPriceCurrency`, `DiscountAmount`, `DiscountPercentage`, `EnergyEfficiencyClass`, `QualifiedPrograms`, `LotSize`, dimension/weight fields, shipping fields, `UnitPrice`, `UnitPricingMeasure`, `LegacyItemId`, `Alerts`, `SellerAccountType`, `TyreLabelImageUrl`, `PriorityListingPayload`. **`SellerItemRevision` is not Feed-exclusive** — it's also on Browse API's `Item` (detail) schema, see the Browse section above; it just happened to get written down here first, which is the only reason an earlier pass through this conversation wrongly assumed it was Feed-only without ever checking Browse.
- **Correction of an earlier wrong claim:** initially assumed (from a secondhand web-search *summary* of the Feed SDK's README, not the real data) that the feed only includes one image field (`DefaultImageUrl`). Verified wrong via a real call — the schema has both `ImageUrl` (primary) and `AdditionalImageUrls` (plural). Lesson: don't trust a secondhand summary of API docs over an actual call when one's available to make.
- **`LocalizedAspects` is base64-encoded key:value pairs** (item specifics) — e.g. a real test row decoded to `Colour: Dark Teal`, `Material: Rayon`, `Type: Embroidery, Machine`. Could plausibly carry CPU/RAM specs for server listings if sellers fill them in — **unconfirmed for real server-category listings**, since sandbox only returns synthetic, category-unrelated data (the test row for category 58058 was a sewing-thread listing, not a computer).
- **Scale is real and large.** The official SDK's own performance numbers: category bootstrap files range from 2.3MB/24K records up to 4.66GB/63.2M records; a single day's `NEWLY_LISTED` file for one mid-size category was already 55K records. Needs real infrastructure (chunked download/reassembly, a query engine to filter locally) to use at all — not a quick background-job call. (Compute isn't the actual constraint for this project — Shadesmar has plenty — but the file sizes and the lack of a keyword-level filter are real regardless of available hardware.)
- **No official Ruby SDK exists anywhere in eBay's GitHub org** (confirmed by listing it directly — only Java/Python `FeedSDK`). A third-party gem, `hakanensari/ebay-ruby`, covers Browse API with OAuth + a `.sandbox` switch, but isn't an official eBay SDK — per the project rule ("unless it's a legit eBay sdk I dont want it"), not adopted.
- **Status: promising enough not to rule out for revisiting the category-sweep punt — not decided.** The original reason category sweeps got punted (per-item "show" cost for mostly-noise results) doesn't apply the same way here — it's a bulk file, not per-item calls, and it genuinely carries multiple images + structured aspects, contrary to the earlier wrong assumption. But real-world usefulness (do sellers actually fill in `LocalizedAspects` for server listings) can't be verified until production access exists, since sandbox data is synthetic and category-unrelated.

## Tooling gotcha

eBay's own official docs (`developers.ebay.com`, `developer.ebay.com`, `edp.ebay.com`) all block automated fetching — 403 or DNS failure on every URL variant tried. eBay's own official open-source SDK repos on GitHub (Node OAuth client, Java/Python Feed SDK) and third-party mirrors of the raw OpenAPI spec are more reliable sources for verifying exact API behavior than trying to fetch the doc pages directly.
