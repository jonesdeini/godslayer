# godslayer — eBay homelab deal scanner

A living plan. Update this file as decisions actually get made in conversation — don't treat it as finished, and don't let it get stale.

## What this is

Scans eBay listings for underpriced/mislisted homelab gear (DDR4-era Xeon servers & workstations, ECC RDIMMs) by reading the *listing photos* (BIOS/iLO screens, DIMM labels) instead of trusting the title or price. Sellers often get specs wrong in both directions; the photos tell the truth.

The motivating real-world example (a specific listing + exactly how its claimed spec didn't hold up against the one photo that actually shows it) lives in `secret_sauce/motivating-example.md` (gitignored, same reason as everything else in `secret_sauce/` below — the general framing is fine public, a fully worked example of the exact signal isn't).

## Decided so far

**Services, and why Rails is the whole app right now:**
- Rails app lives at the repo root (module `Godslayer`, `rails new .`). It is the *only* thing with database credentials, full stop — not just migrations/`schema.rb` (ActiveRecord migrations, not `structure.sql`), but all reads and writes, for every table.
- The scraper is **Ruby code inside this same Rails app** (a service object + a recurring Solid Queue job, not a separate process) — for now. Reasoning: a separate Go service sharing the same Postgres instance is a real anti-pattern (schema becomes an untyped cross-language contract, no enforcement beyond convention that a service only writes what it owns). Collapsing the scraper into Rails deletes that problem entirely for this boundary, and Ruby is perfectly adequate for a politely-rate-limited I/O-bound poller — there's no concurrency win from Go here worth the cross-language coupling.
- Go is **deferred, not cancelled**. If/when it comes back (for practice, or because of an actual limitation hit in Ruby), it comes back as a real separate service that talks to Rails **over an HTTP API that Rails exposes — it never touches Postgres directly.** That turns "don't write what you don't own" from a convention into something enforced by construction (Go simply has no DB credentials to misuse), and turns schema drift into a normal, well-tooled API-versioning problem instead of a cross-language ORM-drift problem.
- Explicit reasoning for the sequencing, not just "Ruby is easier": the Go-with-a-pushing-API architecture is the *better end state* — but validating the eBay integration and the data model is the risky, uncertain part right now, and the Ruby-in-Rails version gets that validated fastest with the least thrown away. Once the data model's proven out, swapping the producer (Ruby job → Go service hitting the same API) is a clean, well-scoped change that doesn't touch the consumer side at all. Ship the uncertain part cheaply first; the better architecture is still coming, deliberately, not abandoned.
- Python ML worker (`ml/`) — built and actually running in production (see State of repo). Python talks to Rails **over an HTTP API, never touches Postgres directly** — same reasoning already applied to Go above, no special exemption just because it's a different language. The write-back endpoint shape (what a "determination" looks like) is decided and built too, see State of repo's `POST /api/listings/:id/determinations` entry.
- **Work distribution is a real message broker (RabbitMQ), not a hand-rolled claim table.** Decided over Kafka specifically: this is a work-queue problem (N workers each claim and finish one discrete unit of work, exactly what RabbitMQ's native ack/requeue/dead-letter semantics are built for), not an event-log/replay problem (Kafka's actual strength) - reaching for Kafka here would mean doing RabbitMQ's job worse, with more operational complexity, not less. Decided over hand-rolling `SELECT ... FOR UPDATE SKIP LOCKED` claiming ourselves: that's reinventing a worse, less battle-tested subset of what RabbitMQ already does correctly (claim timeouts, redelivery on worker crash) for the cost of one more container - a good trade given this project's actual purpose includes learning real infra, not just shipping. **Publishing is no longer inline on import (PR #13) - it's gated on images actually being downloaded.** `ListingImporter` only schedules `ListingImageDownloadJob`; that job downloads every image for a listing via Active Storage and stamps `images_downloaded_at` only once all of them succeed (a partial failure leaves it unset, not a false positive). A periodic `PublishReadyListingsJob` batches listings with images downloaded but not yet published (`images_downloaded_at` set, `published_at` nil), opens **one** RabbitMQ connection for the whole batch, and stamps `published_at` on each row immediately after its own successful publish - a mid-batch failure only leaves the genuinely-unsent ones flagged for the next run. `Rabbitmq::ListingReadyPublisher#publish_batch(listings)` replaces the old single-item `#publish(listing_id:)`, since nothing calls the single-item form anymore. `ListingImporter` resets `listing.published_at = nil` whenever it's a new record or the revision genuinely changed, so a re-imported/revised listing becomes eligible for republishing again instead of being permanently excluded by the `published_at`-not-nil gate. Tested against `bunny-mock`, not a real broker - unlike Postgres, there's no per-test transactional isolation for an external queue, so a real-broker test suite was never actually safe under parallel test workers, and the app's own Bunny usage is thin enough (open a connection, declare a queue, publish) that there's little broker-specific behavior worth a live dependency in CI for. `Bunny.new` is monkeypatched to a memoized `BunnyMock` session in `test/support/bunny_mock.rb`, reset per test.
- **Reversed: Rails does download and store image bytes, via Active Storage (PR #13).** The original reasoning (Rails' scraper stage is purely an affordability filter, never looks at a photo) still holds, but a separate problem forced the reversal: eBay's own CDN image URLs aren't permanent, so a Python consumer fetching them lazily - whenever it gets around to a queued listing - risks the images already being gone by then. `ListingImageDownloadJob` downloads every image for a listing and stamps `images_downloaded_at` only once all of them succeed; `PublishReadyListingsJob` gates publishing to Python on that, so Python only ever learns about a listing after Rails already has stable, permanent URLs for it to hand over (served via `GET /api/listings/:id`, see State of repo). Each downloaded image is its own `ListingImage` row (`belongs_to :listing`, `has_one_attached :file`, `source_url` column) rather than a bare `has_many_attached :images` on `Listing` - the dedicated row is what makes "have we already downloaded this exact URL" a plain indexed query instead of something no-ops or re-downloads by accident. Primary vs. additional images are **not** distinguished anywhere past the scraper's own `Listing#primary_image_url`/`#additional_image_urls` (which still read straight off eBay's `raw` response, since eBay's data distinguishes them) - once images are downloaded, they're served as one flat `images` array with no primary flag. Nothing downstream (photo sorter, extraction, scorer) needs to know which photo was eBay's chosen "primary" one; that's a listing-page merchandising concept, not a signal about image content.

**Why not a shared-database "ingester" model generally:** shared-database is a known anti-pattern (implicit untyped contracts, no encapsulation, partial-write visibility to other readers) — it's being avoided outright for Go by keeping Rails as the sole DB owner, rather than mitigated with DB-level grants/roles. That mitigation (per-service Postgres roles) is still a reasonable fallback to remember if a second service ever does need direct DB access, but it's not the current plan.

**CI:** run the full test suite on every change, no path-based filtering — premature optimization for this scale, and it would undermine the one thing that would actually catch a Rails-vs-everyone-else contract break.

**Repo layout:** the Rails app occupies the repo root. `ml/` is a real `uv` project, the Python consumer side (see Services and State of repo). No `ingester/` directory exists right now — it gets created later, as a sibling, only if/when Go actually comes back as a real API client.

**Secrets:** plain `SECRET_KEY_BASE` env var, not Rails' default `config/credentials.yml.enc` + `master.key`. A deliberate, stated deviation from omakase (see the collaboration rule above) — nothing else was ever stored in credentials.yml.enc, and running two parallel secret mechanisms for one value wasn't worth it. The actual reason it tipped this way: plaintext `.env.example`/`.env.test` diffs are reviewable in git history, an encrypted credentials blob's aren't.

**Deploy:** same shape as reef-1000 — `docker-compose.yml` (postgres + web + jobs + a poll-based `updater`) and a `build_and_push` CI job to GHCR, gated on `lint`/`test`/`scan_ruby` passing. This is going on the same home Unraid box as reef-1000 (Shadesmar), so the same reasoning applies: Kamal-over-SSH would need a path into the LAN for a GitHub-hosted runner to reach, which the `updater` avoids entirely (the box only ever reaches out to `docker pull`, GitHub never executes anything on it). Kamal, Solid Cache, and Solid Cable were all stripped from the Rails 8 defaults — Kamal because it's not the deploy mechanism, Cache/Cable because nothing uses a cache store or ActionCable yet and keeping them would mean provisioning 2 more logical Postgres databases for nothing. Production now has just `primary` + `queue` (Solid Queue, for the recurring scrape job).

**One `docker-compose.yml` for the whole system, Ruby and Python both — not a separate compose file per language.** This is a single-box, single-operator deployment (one Unraid host, no independent per-team deploy loops, no need to scale services independently), which is exactly the case a unified compose file is the standard, not the awkward choice - the "real" microservices pattern of separate repos/CI/deploy pipelines per service solves an organizational scaling problem this project doesn't have, same reasoning already applied to deferring Go/Python into real separate services. `ollama` and `ml` (the Python consumer, see Services above) joined the existing file: `ml` gets the same GHCR-published-image pattern as `web`/`jobs` (its own `build_and_push_ml` CI job, gated on a new `test_ml` job, not gated on the Ruby jobs since the two are independent), and `ollama` uses the public `ollama/ollama` image directly with no custom build. A real Unraid gotcha surfaced setting this up: Shadesmar's Docker runs inside a fixed 20GB virtual disk (`docker.img`), separate from the actual (multi-terabyte) array - that limit only applies to named Docker volumes, not plain bind mounts, so `ollama`'s model storage uses the same `./ollama_data` relative-bind-mount pattern already used for `postgres_data`/`rabbitmq_data`/`storage_data`, not a Docker-managed volume.

**Sandbox/production:** `EBAY_ENVIRONMENT` (`sandbox`/`production`, required) picks which eBay host to hit — `Ebay::Base::API_HOSTS` maps it to one host, since sandbox/production only ever differ by host, never by path. Dev ID (the third part of eBay's credential keyset) isn't used for this OAuth flow. Full research in `docs/ebay-api.md`.

**Search strategy:**
- **Category sweeps are punted, not just deferred in code — there's no `SearchCategory` model at all right now.** Category-only search (no keyword) has no text/relevance matching whatsoever — it's literally "fetch every active listing in that eBay category, newest first," filtered only by price cap. The one thing it uniquely catches (a seller who doesn't know what model they have, so it'd never surface via keyword) is real, but that signal is buried under huge volume that's either already findable via keyword search anyway, or just irrelevant noise — and *right now*, nothing downstream (no photo sorter, no extraction, no scorer) exists to sift that volume. Paying the cost (API calls, storage, noise) without being able to realize the benefit isn't worth it yet. Revisit once there's a real pipeline stage that can use the volume.
- Keyword sweeps (`search_keywords`) run unrestricted — no category filter on a keyword search either, since that would cost real recall (missing a correctly-labeled listing that got miscategorized) for little precision gain given how specific the actual keywords are (model numbers, misspellings, RAM part numbers).
- Price cap is a single global env var (e.g. `PRICE_CAP_CENTS`), not per-search-term — it's a scalar affordability threshold ("can we afford to even look at this"), not a growing collection, so it follows the config-not-DB-settings reasoning rather than the search-terms-as-data reasoning below.
- Keywords are modeled as their own DB table/resource (`search_keywords`), not an env var — it's a growing, edited-over-time collection (not a single-tenant config scalar — see reef-1000's "config, not database-backed settings" principle, which this *doesn't* contradict since that rule was about identity/credential scalars, not collections with their own lifecycle). If category sweeps come back later, decide then whether they're worth a `SearchCategory` table of their own again, rather than assuming the old shape still applies.

**Funnel stages, clarified:** scraper (now) is purely an affordability filter — "get everything that fits our search criteria and the price cap." The photo sorter (plan's phase 2) classifies which photos are even useful, no value judgment yet. Extraction (phase 3) reads the true specs off those photos. A **deal scorer** (the plan's own "Later" phase) is a distinct fourth stage — diffing extracted true specs against current market prices for those specific components to actually rank deals. That only works if extraction produces structured fields (e.g. "4x 32GB DDR4 RDIMM"), not prose — worth keeping in mind for how extraction gets designed later, nothing to act on now.

**Exclude phrases — schema, UI, and seeder built and merged (PR #4), real list seeded in production as of 2026-11-02:** some keywords should exclude listings matching a phrase (e.g. "no ram"), **per-keyword, not global** — real pricing research shows why CPU-only value varies across the platforms this project targets, so a "no ram" exclusion that's safe for one keyword (common mid-tier CPUs) would wrongly discard a genuinely good deal for another (rare top-bin chips). Mitigation for that risk: add dedicated keywords for the specific high-value chips *without* the exclusion, as a free safety net (keyword sweeps aren't mutually exclusive, the upsert is idempotent). Schema settled: `exclude_phrase`, a nullable `string` column on `search_keywords` (not an array, not a separate table). **`-term` exclusion syntax AND OR-grouping/AND on the `q` param are both confirmed working, server-side, verified with real calls (2026-10-26, 2026-10-27)** — eBay genuinely filters excluded listings out before they reach the response. The OR-group finding matters beyond precision: one `search_keywords` row can now cover every spacing/capitalization variant of a model name in a single API call (`(modelA,"model A") (genX,"gen X",gX,"g X")`), which is the likely mechanism for staying under the 5,000/day rate limit. Full research in `docs/ebay-api.md`. The real target keyword list (which models, which exclude phrases) lives in `secret_sauce/search_terms.json` (gitignored - not for the public repo) and gets loaded via `rails search_keywords:seed` (`SearchKeywordSeeder`, idempotent - upserts by phrase, deactivates anything missing from the file rather than deleting). Vendor/DDR4-generation research is in `secret_sauce/target-hardware.md` (gitignored, not `docs/` - the curated list of which specific models across vendors is itself the sauce, even though any single generation-to-RAM-type fact is public on its own).

**Controllers: no ivars in action bodies, a deliberate deviation from Rails' own scaffold convention.** Every action uses explicit `render locals: { ... }` (or `redirect_to`) instead of relying on Rails' implicit render auto-exposing instance variables to the view. The reasoning: an ivar set in a controller action and read in its view is an implicit contract between the two — invisible at either call site, only discoverable by knowing Rails' convention or grepping both files. An explicit `locals:` hash makes that contract visible exactly where the view gets chosen. The one exception is a single memoized private method (e.g. `search_keyword`) when an action needs to build-or-find a record once and reuse the *same* instance across a save attempt, a redirect, and a possible re-render-on-failure — memoization in Ruby means an ivar either way, but it stays contained to one line, never written directly in an action body. First applied in `SearchKeywordsController`.

## Open / not yet decided

- **Whether the eBay Feed API is worth building on, for revisiting the category-sweep punt.** Promising enough not to rule out — it's a bulk-file mechanism (not per-item calls), genuinely carries multiple images + structured item-specifics data (corrected an earlier wrong assumption that it only had one image). Not decided, since real-world usefulness can't be verified until production access exists (sandbox only returns synthetic, category-unrelated data). Full findings in `docs/ebay-api.md`.
- Rate limiting is a real, hard constraint on the keyword-sweep design (Browse API default: 5,000 calls/day, shared across every call the app makes) — not yet designed around with real numbers (how many active keywords × "show" calls per sweep × how often). Server-side `-term` exclusion (confirmed working) is the likely mitigation once exclude phrases are built, but the budget math itself hasn't been worked out.
- **The write-back shape is decided and built (see State of repo). Consumer-side reliability is also built now - see `docs/python-consumer.md`'s "Consumer reliability" section for the full incident writeup.** Python consumes directly from RabbitMQ (not an HTTP polling endpoint - see Services above), fetches a listing's actual data (including downloaded image URLs, via the `images` array) through `GET /api/listings/:id`, using just the `listing_id` carried in the queue message, and posts its findings to `POST /api/listings/:id/determinations`. `consumer.py`'s `run` traps `SIGTERM`/`SIGINT` and calls `channel.stop_consuming()` (pika's own documented pattern for a `BlockingConnection`) - the in-flight message's callback still runs to completion and acks normally, only the *next* delivery is refused, so a deploy's `docker stop` doesn't kill a listing mid-processing (same role Solid Queue's own built-in graceful termination plays for `jobs`, just not free on the Python side, had to be added). Separately, a real production incident (2026-11-02) found 757 listings silently discarded by one ~4-second `web` outage during a deploy - `handle_message`'s bare `except Exception` acked on every failure, transient or permanent, with no retry. Fixed: default to retrying, carving out known-permanent exceptions (currently: a 4xx `HTTPError`) as the exception, not an allowlist of known-retryable ones, since a retry-count cap (`MAX_ATTEMPTS = 3`) already bounds the cost of retrying something that was never going to work; retries happen in-process with a short fixed delay (`RETRY_DELAY_SECONDS = 5`, not exponential, not a RabbitMQ delay queue or plugin - the only outage observed so far is ~4 seconds, not worth building delay infrastructure for a longer one that hasn't happened); exhausted retries land in a durable `listing_ready.dead` queue rather than being discarded. The read and write APIs both have no auth yet - fine for now at this trust level (same LAN as everything else), worth a real look before either is reachable from anywhere less trusted. **The old "unprocessed tracking" gap (RabbitMQ unreachable at the exact moment of import, so a first-seen listing never got retried) is resolved by construction now** - publishing isn't on the import path at all anymore (see Services above), so a broker outage just delays `PublishReadyListingsJob`'s next batch rather than silently dropping anything. **A narrower version of the same class of gap still exists, not yet addressed:** a permanent image-download failure (404, timeout, no retry configured on `ListingImageDownloadJob`) leaves `images_downloaded_at` unset forever, which means that listing never becomes eligible for `PublishReadyListingsJob` either - same silent-gap shape, just relocated one stage earlier.
- **Python consumer's pipeline shape and design notes (discussed 2026-10-29 through 31)** — full writeup in `docs/python-consumer.md`. All 6 steps are built now: consume, call the read API, download images, OCR, extraction/comparison, and write the determination back via `POST /api/listings/:id/determinations`. **Local models only, not hosted APIs, for anything in this pipeline** — a real cost constraint (Rob is job-searching while building this), not a style preference. The comparison step splits across a local LLM (via Ollama, fuzzy text extraction/normalization) and plain code (deterministic unit conversion + threshold comparison) — a single model call asked to extract, convert units, and judge all at once was tested for real and reliably failed in different ways each time; narrowing each model call to one job and moving arithmetic into code fixed it. Specifics (schema, model choice, prompts) are in the gitignored `secret_sauce/mvp-strategy.md`.
- **The review UI itself - a barebones version is built (PR #18), not "not discussed" anymore.** A read-only `ListingsController` (index + show), same conventions as `SearchKeywordsController` (no ivars, `render locals:`, plain ERB). Index sorts match/mismatch above no_evidence/pending instead of filter UI - with far more `no_evidence` rows than real matches/mismatches in the first production sweep, plain chronological order would bury the only rows worth looking at. Still open: any real triage workflow (marking a listing reviewed/acted-on, filtering, pagination) - this is deliberately just "can Rob see the results," nothing more yet.

This is what the Python consumer calls with the `listing_id` it gets off the RabbitMQ queue.
- **`POST /api/listings/:id/determinations` exists - the write-back endpoint Python posts its findings to.** Settled the previously-open write-back shape: `determinations` is append-only (a reprocessed listing gets a new row, not an overwritten one), with a boolean `active` flag marking the current one per `listing_id`+`field` - enforced by a partial unique index (`where: active`), not just application logic, so a bug in the write path fails loudly instead of silently leaving two rows active. `field` is a plain string (`"ram"` for now) rather than a dedicated column or table per spec type, so adding CPU/storage determinations later doesn't need a schema change. Columns hold the raw claimed/photo value+unit pairs (e.g. `claimed_value: 16, claimed_unit: "GB"`), not a pre-converted MB figure - keeps the row auditable against what was actually seen, with unit conversion staying a pure function in Python (`determinations.py`) rather than something baked into storage. `listing_image_id` (nullable - a `no_evidence` verdict has no hit) records which specific downloaded image produced the photo-side evidence. `DeterminationWriter` (service object, same shape as `ListingImporter`) does the deactivate-old/create-new as one transaction, ordered so the old row is deactivated before the new one is inserted - never two active rows for the same `listing_id`+`field` even transiently.
- **Images are downloaded and stored by Rails itself (PR #13), not fetched lazily by Python from eBay's CDN** - see the reversed decision under Services above. Each image is its own `ListingImage` row (`listing_images` table: `listing_id`, `source_url`, unique together) wrapping a single `has_one_attached :file`, rather than a bare `has_many_attached :images` on `Listing` directly - the dedicated row is what lets `ListingImageDownloadJob` check "already downloaded this URL?" as a plain query before ever hitting the network, which also makes re-imports/retries idempotent instead of duplicating attachments.
